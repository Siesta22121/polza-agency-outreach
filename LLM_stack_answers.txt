3. Пример сравнения (Claude vs GPT для парсинга):

Задача: "Напиши Python-функцию для парсинга таблицы с постраничной навигацией"

Claude 3.5 Sonnet:
- 1 попытка: рабочий код с BeautifulSoup + requests
- Код готов к production: да (обработка ошибок, таймауты, retry)
- Время: 8 секунд

GPT-4o:
- 1 попытка: рабочий, но без обработки пагинации
- 2 попытка (уточнение): полный код с пагинацией
- Код готов к production: с доработками
- Время: 12 секунд + уточнение

Вывод: Claude быстрее и точнее с первого раза, GPT требует 2-3 итерации.

7. Какие метрики для тебя важны?

- Precision первого ответа (не нужно переспрашивать)
- Глубина понимания контекста (не теряет нить диалога)
- Стоимость токенов (output дешевле не значит лучше)
- Количество итераций до готового решения
- Комфорт работы (UX интерфейса, скорость ввода/вывода)

8. Какие тесты ты потребуешь для новой функции?

Unit-тесты (pytest):
- Каждая публичная функция/метод покрыта
- Edge cases: пустые входные, None, исключения
- Моки для внешних запросов (API, БД)

Integration-тесты:
- Взаимодействие между модулями
- Реальные вызовы к API (с изоляцией)
- Работа с файловой системой

E2E-тесты:
- Полный сценарий: от запуска до результата
- Smoke-тесты для критических путей

9. Какой процент покрытия считаешь достаточным?

- Unit: 85% (критичные модули — 95%+)
- Integration: 60% (все основные сценарии)
- E2E: 20% (только критические сценарии)

Не гонюсь за 100% — важнее качество тестов, чем количество.

10. Пример тест-кейса для функции парсинга сайтов:

'''python
def test_parse_page_success():
    """Корректный HTML -> словарь с данными"""
    html = "<html><h1>Компания</h1><p>Описание</p></html>"
    result = parse_page(html, schema={"title": "h1", "desc": "p"})
    assert result == {"title": "Компания", "desc": "Описание"}

def test_parse_page_empty():
    """Пустой HTML -> пустой словарь"""
    assert parse_page("", {}) == {}

def test_parse_page_missing_element():
    """Нет элемента в HTML -> None"""
    result = parse_page("<html></html>", {"title": "h1"})
    assert result["title"] is None

def test_parse_page_invalid_html():
    """Битый HTML -> не падает, парсит что может"""
    result = parse_page("<html><p>текст</html>", {"text": "p"})
    assert result["text"] == "текст"

def test_parse_page_network_error():
    """Таймаут/ошибка сети -> исключение"""
    with pytest.raises(ConnectionError):
        parse_page("http://not-exist.local", {}, timeout=0.1)

11. Какие разрешения ты дашь coding-агенту, имеющему доступ к терминалу и базе?

Принципы безопасности:
- Минимальные привилегии (Principle of Least Privilege)
- Read-only по умолчанию, write по запросу
- Аудит всех изменений (git log)

Конкретные разрешения:
✅ Чтение файлов (кроме .env, .git, secrets)
✅ Запуск тестов (pytest, npm test)
✅ Git diff/status/log (только read)
❌ Удаление файлов (rm -rf, drop table)
❌ Изменение БД напрямую (только через миграции)
❌ Доступ к production (только read-only)
❌ Публикация зависимостей (pip publish, npm publish)
✅ Создание файлов в temp-директориях
✅ Коммиты (с code-review перед push)

Разграничение dev/staging/prod:
- Dev: полный доступ (write, execute)
- Staging: read + write через CI/CD, без прямого доступа к терминалу
- Prod: только read (логи, метрики), deploy через CI/CD с approval

12. Пишешь ли ты автоматические тесты и включаешь ли их в CI/CD?

Да. Все тесты проходят в CI/CD перед слиянием.

Проверки перед слиянием PR:
- ✅ Все unit-тесты проходят (pytest / jest)
- ✅ Линтер без ошибок (ruff / eslint)
- ✅ typecheck проходит (mypy / TypeScript strict)
- ✅ Integration-тесты проходят
- ✅ Код-стайл соответствует проекту (форматтер)
- ✅ SonarQube: нет critical/bug issues
- ✅ Зависимости проверены (pip audit / npm audit)

Что делаю при падении тестов:
1. Смотрю лог ошибки
2. Воспроизвожу локально
3. Если тест нестабильный (flaky) — добавляю retry и отмечаю
4. Если тест на новую функциональность — фикшу код
5. Если тест сломался из-за изменений — фикшу тест
6. Перед повторным merge — полный прогон CI/CD

CI/CD стэк:
- GitHub Actions (основной)
- GitLab CI (для проектов на GitLab)
- pre-commit хуки (ruff, mypy, pytest quick)
- Dependabot на автоматическое обновление зависимостей
