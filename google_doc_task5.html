Почему перешёл:

  • Добавил DeepSeek Coder: быстрый, дешёвый, хорош для рефакторинга и написания тестов

6. Как сравниваешь две новые модели или инструмента?

Методология тестирования:

  1. Написать функцию парсинга HTML по заданной схеме
  2. Рефакторинг legacy-кода (100+ строк)
  3. Объяснить архитектуру по коду без документации
  4. Сгенерировать сложный SQL-запрос с JOIN и подзапросами
  5. Написать Dockerfile + docker-compose для микросервиса
  6. Найти баг в предоставленном коде (заведомо сломанном)

Метрики: TTFR (время первого ответа), количество попыток до рабочего решения, соответствие код-стайлу (1-5), % кода в продакшн без изменений, стоимость запроса.

Пример сравнения (Claude vs GPT на парсинге):

Задача: "Напиши Python-функцию для парсинга таблицы с постраничной навигацией"

Claude 3.5 Sonnet: 1 попытка — рабочий код с BeautifulSoup + requests, готов к production (обработка ошибок, таймауты, retry). Время: 8 секунд.

GPT-4o: 1 попытка — рабочий, но без обработки пагинации. 2 попытка (уточнение) — полный код. С доработками. Время: 12 + уточнение.

Вывод: Claude быстрее и точнее с первого раза, GPT требует 2-3 итерации.

7. Какие метрики для тебя важны?

  • Precision первого ответа (не нужно переспрашивать)
  • Глубина понимания контекста (не теряет нить диалога)
  • Стоимость токенов (output дешевле не значит лучше)
  • Количество итераций до готового решения
  • Комфорт работы (UX интерфейса, скорость ввода/вывода)

8. Какие тесты ты потребуешь для новой функции?

Unit-тесты (pytest): каждая публичная функция покрыта, edge cases (пустые, None, исключения), моки для внешних запросов.

Integration-тесты: взаимодействие между модулями, реальные вызовы к API (с изоляцией), работа с файловой системой.

E2E-тесты: полный сценарий от запуска до результата, smoke-тесты для критических путей.

9. Какой процент покрытия считаешь достаточным?

Unit: 85% (критичные модули — 95%+). Integration: 60% (все основные сценарии). E2E: 20% (только критические сценарии). Не гонюсь за 100% — важнее качество тестов, чем количество.

10. Пример тест-кейса для функции парсинга сайтов

def test_parse_page_success():
    """Корректный HTML -> словарь с данными"""
    html = "<html><h1>Компания</h1><p>Описание</p></html>"
    result = parse_page(html, schema={"title": "h1", "desc": "p"})
    assert result == {"title": "Компания", "desc": "Описание"}

def test_parse_page_empty():
    """Пустой HTML -> пустой словарь"""
    assert parse_page("", {}) == {}

def test_parse_page_missing_element():
    """Нет элемента -> None"""
    result = parse_page("<html></html>", {"title": "h1"})
    assert result["title"] is None

def test_parse_page_network_error():
    """Таймаут -> исключение"""
    with pytest.raises(ConnectionError):
        parse_page("http://not-exist.local", {}, timeout=0.1)

11. Какие разрешения ты дашь coding-агенту?

✅ Разрешено: Чтение файлов (кроме .env, secrets), запуск тестов, git diff/status/log, создание файлов в temp, коммиты (с code-review).

❌ Запрещено: Удаление файлов, прямые изменения БД, доступ к production (только read-only), публикация зависимостей.

Разграничение сред: Dev — полный доступ. Staging — read + write через CI/CD. Prod — только read, deploy с approval.

12. Автоматические тесты и CI/CD

Проверки перед слиянием PR:

  • Все unit-тесты проходят (pytest)
  • Линтер без ошибок (ruff)
  • Typecheck (mypy strict)
  • Integration-тесты проходят
  • Код-стайл соответствует проекту
  • SonarQube: нет critical/bug issues
  • Зависимости проверены (pip/npm audit)

При падении тестов: смотрю лог → воспроизвожу локально → flaky тесты с retry → фикшу код или тест → полный прогон CI/CD.

CI/CD стэк: GitHub Actions (основной), GitLab CI (для GitLab-проектов), pre-commit хуки (ruff, mypy, pytest quick), Dependabot.
